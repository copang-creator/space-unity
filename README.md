Client를 기반으로 개발하는 멀티플레이어 온라인 게임 프로젝트입니다.

> **개발 환경:** macOS 27.0.1 · VS Code · .NET 10 SDK · Unity Editor 6.6

> **게임 형태:** Unity 3D Space Shooter\

## 프로젝트 목표

장시간 플레이가 가능한 Unity 기반 멀티플레이어 Space Shooter를
개발합니다.

핵심 목표:

-   한 번의 플레이 세션이 **1시간 이상** 지속될 수 있는 게임 구조를 지원합니다.
-   플레이 도중 언제든지 게임 내 상점에서 아이템을 구매할 수 있도록 합니다.
-   인증, 캐릭터, Lobby, Room, 상점 등 게임 서비스 기능은 .NET 서버가 관리합니다.
-   실시간 게임 월드와 게임 플레이 패킷 처리는 Unity Dedicated Server가 담당합니다.
-   채팅은 SignalR, 게임 플레이 실시간 통신은 NGO와 Unity Transport를 사용합니다.
-   초기에는 로컬 컴퓨터에서 `localhost` 기반으로 개발하고, 이후 AWS 환경에 배포합니다.

패키지의 정확한 버전은 고정된 것으로 간주하지 않습니다. 실제 프로젝트
생성 시점에 .NET 10 및 Unity 6.6과의 호환성을 확인한 뒤 결정하고
기록합니다.

### 통신 경로와 책임
``` text
  -----------------------------------------------------------------------
  통신 경로                  프로토콜/형식              책임
  ----------------------- ----------------------- -----------------------
  Unity Client ↔          gRPC (Protobuf)         인증(JWT), 캐릭터,
          .NET Server                             Lobby/Room 관리, 상점
                                                  등 요청·응답

  Unity Client ↔          SignalR (JSON)          Lobby 및 Room 채팅,
     .NET SignalR Hub                             실시간 서비스 알림

  Unity Client ↔          NGO + Unity Transport   게임 플레이 패킷 및
  Unity Dedicated Server  (UDP)                   네트워크 오브젝트
                                                  동기화

  Unity Dedicated Server  gRPC                    Room 프로세스 등록,
  ↔ .NET Server                                   상태 보고, 서비스 연동
  -----------------------------------------------------------------------
```
**통신 경계 원칙**

-   일반 게임 서비스 요청과 영속 데이터 변경은 .NET 서버를 기준으로
    처리합니다.
-   채팅 및 실시간 서비스 알림은 SignalR Hub를 통해 전달합니다.
-   프레임 단위 게임 상태와 게임 플레이 네트워크 동기화는 Unity
    Dedicated Server가 담당합니다.
-   Client는 신뢰할 수 있는 권한 주체가 아닙니다. Client가 보낸 값만으로
    소유권, 재화, 아이템, 피해량 또는 게임 결과를 확정하지 않습니다.

## 프로젝트 경계와 계약

통신 계약은 사용 목적에 따라 분리합니다.

### `Server.ContractsMessage`

-   SignalR에서 사용하는 JSON DTO를 정의합니다.
-   Unity Client와 .NET Server가 함께 참조할 수 있도록 구성합니다.
-   클라이언트와 서버 사이에서 공유하는 메시지의 이름, 필드, 의미 및
    호환성 규칙을 관리합니다.
-   서버 내부 구현 타입이나 DB Entity를 외부 계약으로 직접 노출하지
    않습니다.

### `Server.ContractsProto`

-   gRPC 및 Protobuf 계약을 정의합니다.
-   현재 설계에서는 서버 전용 계약 라이브러리로 분리합니다.
-   인증, 캐릭터, Room, 상점 및 Dedicated Server 연동 등에 필요한
    서비스와 메시지를 정의합니다.
-   `.proto` 변경 시 생성 코드와 호출 측 호환성을 함께 확인합니다.

### 권장 논리적 계층

``` text
GameServer.sln
├─ Server.ContractsMessage/    # SignalR JSON DTO 공유 계약
├─ Server.ContractsProto/      # gRPC / Protobuf 계약
├─ GameServer.*                # .NET 서비스 및 도메인 계층
├─ UnityClient/                # Unity 6.6 Client
└─ UnityDedicatedServer/       # Unity Dedicated Server
```

위 구조는 논리적 경계 예시입니다. 실제 디렉터리와 프로젝트 이름은 구현
단계에서 확정하되, 계약·서비스·인프라·Unity 실행 환경의 책임을 혼합하지
않습니다.

## 게임 흐름

### 1. 접속 및 인증

1.  Unity Client가 .NET gRPC 서버에 직접 접속합니다.
2.  인증 요청을 보내고 서버가 사용자 자격 증명을 검증합니다.
3.  인증에 성공하면 서버가 JWT를 발급합니다.
4.  이후 인증이 필요한 요청은 토큰을 이용해 서버에서 검증합니다.
5.  서버는 토큰의 유효성뿐 아니라 요청 대상에 대한 권한도 매번
    확인합니다.

### 2. 캐릭터 및 Lobby

1.  사용자는 캐릭터를 생성하거나 기존 캐릭터를 선택합니다.
2.  선택한 캐릭터로 Lobby에 입장합니다.
3.  Lobby 채팅은 Unity Client와 .NET SignalR Hub 사이에서 JSON 메시지로
    처리합니다.
4.  Room 목록과 Room 상태는 .NET 서버의 관리 데이터를 기준으로
    조회합니다.

### 3. Room 입장 및 생성

1.  Client는 Room 목록을 조회합니다.
2.  사용자는 공개된 Room을 선택해 입장하거나 새 Room 생성을 요청합니다.
3.  Room 생성과 입장 가능 여부는 .NET 서버가 검증합니다.
4.  Room Owner는 Room 잠금/해제 권한을 가집니다.
5.  잠금 상태에서만 게임 시작이 가능하도록 규칙을 적용합니다.
6.  Room 채팅도 SignalR Hub를 통해 처리합니다.

### 4. 게임 시작 및 Dedicated Server 연결

1.  Room Owner가 잠금 상태의 Room에서 게임 시작을 요청합니다.
2.  .NET 서버가 요청자의 Owner 권한, Room 상태, 참가자 상태 및 시작
    조건을 검증합니다.
3.  Unity Dedicated Server 측에서 해당 Room을 처리할 Room 프로세스를
    생성하거나 할당합니다.
4.  Room 프로세스는 UDP 7000\~8000 범위에서 사용 가능한 포트를 직접
    바인딩합니다.
5.  바인딩에 성공하면 실제 사용한 IP와 포트를 .NET 서버에 gRPC로
    보고합니다.
6.  .NET 서버는 참가 Client에게 접속 정보를 전달합니다.
7.  Client는 전달받은 IP:Port로 Unity Dedicated Server에 접속합니다.
8.  게임 진행 중의 실시간 네트워크 처리는 NGO와 Unity Transport가
    담당합니다.

### 5. 게임 중 상점 이용

-   플레이 중 언제든지 상점 UI를 열 수 있어야 합니다.
-   구매 요청은 Client가 직접 확정하지 않고 .NET 서버에 요청합니다.
-   서버는 가격, 보유 재화, 구매 제한, 아이템 상태 및 중복 요청 여부를
    검증합니다.
-   구매 성공 시 영속 데이터와 게임 세션에 반영할 상태를 일관성 있게
    갱신합니다.
-   게임 중 구매한 아이템의 게임 내 반영 시점과 반영 주체는 서버 권위
    규칙에 따릅니다.

## Room 및 Dedicated Server 운영

### Room 프로세스와 포트

-   Room은 논리적인 게임 방 단위입니다.
-   Room 프로세스는 실제 게임 월드 시뮬레이션과 NGO 네트워크 세션을
    담당합니다.
-   Room 프로세스가 UDP 포트를 직접 바인딩하고, 운영체제가 허용한 범위
    내에서 사용 가능한 포트를 확보합니다.
-   포트 바인딩 실패 시 다른 포트를 시도하거나 생성 실패를 상위 관리
    계층에 보고해야 합니다.
-   .NET 서버는 Room ID와 프로세스 ID, 서버 주소, 포트, 상태를 연계해
    관리합니다.
-   프로세스 종료, 연결 끊김, 비정상 종료 및 재시작에 대한 정리 절차가
    필요합니다.

### 네트워크 방화벽

배포 환경에서는 게임 서버 인스턴스에 UDP 7000\~8000 포트 범위를 허용하는
규칙을 구성하는 것을 기본 방향으로 합니다.

> 포트 범위 규칙 하나로 관리할 수 있다는 것은 운영 편의상의 목표입니다.
> AWS 보안 그룹, 호스트 방화벽, 컨테이너/프로세스 네트워크 구성 및 실제
> 바인딩 주소가 모두 일치하는지 배포 환경에서 검증해야 합니다.

### 상태 관리 원칙

-   Room의 생성·잠금·시작·종료 상태 전이는 서버가 통제합니다.
-   Room Owner 권한은 Client UI 표시가 아니라 서버 측 권한 검사로
    보장합니다.
-   동일 Room에 대한 중복 시작 요청을 방지합니다.
-   프로세스 생성 요청과 포트 등록은 재시도 및 중복 요청에 안전하도록
    설계합니다.
-   서버가 보고한 실제 접속 주소만 Client에 전달합니다. 클라이언트가
    임의로 지정한 주소를 신뢰하지 않습니다.

## 보안 및 개발 원칙

### Client 비신뢰

모든 Client 입력은 변조되거나 재전송될 수 있다고 가정합니다.

-   인증 및 권한 검증은 서버에서 수행합니다.
-   Owner, 관리자, 아이템 소유권 및 재화 변경을 Client 판단에 맡기지
    않습니다.
-   가격, 보상, 피해량, 쿨다운, 이동/행동 제한 등 중요 게임 규칙은 서버
    권위로 처리합니다.
-   요청 크기, 문자열 길이, 숫자 범위, 열거형 값 및 상태 전이를
    검증합니다.
-   반복 요청, 재전송, 중복 구매 및 중복 게임 시작을 방어합니다.
-   인증 토큰과 민감 정보를 로그에 평문으로 남기지 않습니다.

### 계층 분리

-   gRPC 서비스는 전송 계층과 애플리케이션 로직을 분리합니다.
-   SignalR Hub는 연결 및 메시지 전달을 담당하고, 게임 규칙은 별도
    서비스에서 처리합니다.
-   DB 접근은 인프라 계층에 캡슐화합니다.
-   Unity Client UI와 네트워크 서비스 코드를 분리합니다.
-   Dedicated Server의 게임 시뮬레이션과 .NET 게임 서비스 관리 책임을
    구분합니다.

### 비동기 및 스레드 안전성

-   I/O 작업은 가능한 비동기 API를 사용합니다.
-   공유 상태의 동시 접근을 명시적으로 설계합니다.
-   `DbContext`를 여러 스레드에서 동시에 공유하지 않습니다.
-   Room/Session 상태 변경은 원자성, 동시성 제어 및 명확한 소유권을
    갖도록 구현합니다.
-   취소 토큰, 타임아웃, 재시도 정책 및 예외 경계를 정의합니다.
-   fire-and-forget 작업은 예외 관찰과 종료 처리가 보장되지 않는 한
    사용하지 않습니다.

## 개발 환경 및 실행 전략

### 로컬 개발

초기 개발은 단일 개발 컴퓨터에서 각 구성 요소를 실행하는 방식으로
진행합니다.

-   .NET 서버: `localhost`에서 실행
-   SQLite: 로컬 개발 데이터베이스
-   Redis: 로컬 인스턴스 또는 개발용 컨테이너
-   Unity Client: Unity Editor에서 실행
-   Unity Dedicated Server: 로컬 Dedicated Server 빌드 또는 지원되는
    테스트 실행 방식으로 실행

Unity Client와 Dedicated Server의 실제 접속 주소, 포트 및 실행 순서는
개발 환경 설정으로 분리합니다. `localhost`는 같은 컴퓨터 내부
테스트용이며, 다른 장치에서 접속할 때는 해당 장치가 접근 가능한 LAN 주소
또는 배포 주소를 사용해야 합니다.

### 설정 및 비밀 정보

-   환경별 설정은 Development / Production으로 분리합니다.
-   비밀번호, JWT 서명 키, DB 자격 증명 등 비밀 정보는 Git에 커밋하지
    않습니다.
-   로컬 개발에서는 User Secrets 또는 로컬 환경 변수 등을 사용합니다.
-   배포에서는 AWS의 적절한 비밀 관리 수단과 IAM 권한을 적용합니다.
-   실제 운영용 JWT 키와 개발용 키를 공유하지 않습니다.


## 단계별 개발 로드맵

아래 순서는 권장 개발 순서이며, 세부 완료 조건은 각 단계의 구현과
테스트에 맞춰 구체화합니다.

-   [ ] **1단계 --- 솔루션 및 계약 구성**
    -   .NET 10 솔루션과 프로젝트 경계 구성

## 향후 배포 고려 사항

로컬 개발이 안정화된 뒤 AWS 배포 설계를 구체화합니다.

-   .NET 서비스와 Unity Dedicated Server의 배포 단위 및 확장 정책
-   Room 프로세스의 생성·종료·장애 감지·재시작
-   외부 접속용 공인 IP 또는 DNS와 실제 UDP 포트 매핑
-   AWS 보안 그룹의 TCP/UDP 규칙 최소화
-   SQLite 파일의 영속 볼륨, 백업, 복구 및 동시 접근 제약 검토
-   Redis의 접근 제어, 네트워크 격리 및 TLS
-   JWT 키와 기타 비밀 정보의 안전한 보관 및 교체
-   서버 로그, 메트릭, 분산 추적 및 알림
-   배포 자동화와 롤백 절차

특히 SQLite는 초기 개발과 단일 인스턴스 운영에 적합할 수 있지만, 다중
서버 인스턴스에서 공유 데이터베이스로 사용하는 구조에는 제약이 있습니다.
AWS 배포 시에는 동시 쓰기 부하, 파일 시스템 특성, 백업/복구 및 다중
인스턴스 운영 요건을 검증한 뒤 데이터 저장 전략을 확정합니다.
